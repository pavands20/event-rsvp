<!-- sdlc:auto:start overview -->
Event RSVP is a two-app monorepo generated by the Quorq AI SDLC platform: a Vite + React 19 SPA frontend (with Tailwind, React Router, Vitest, and Playwright) and a FastAPI 0.115 backend backed by SQLAlchemy and PostgreSQL (SQLite by default for local runs). The backend defines auth, event management, guest list, and public RSVP routes (some still stubs returning 501), while the frontend renders approved screens on seeded sample data with a ready-to-wire API client. Deployment is handled by a GitHub Actions workflow that builds a Docker image for the backend and publishes the frontend to AWS Amplify via OIDC authentication.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js 20+ (for the frontend)
- Python 3.12+ (for the backend)
- Docker and Docker Compose (optional, for PostgreSQL via docker-compose.yml)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. cd frontend && npm install
2. cd ../backend && pip install -r requirements.txt
3. cp .env.example .env and fill in any required values (e.g. DATABASE_URL, ALLOWED_ORIGINS) if customizing
4. Optional: docker compose up -d to start a local PostgreSQL 16 instance on port 5432
5. Run the frontend dev server: cd frontend && npm run dev
6. Run the backend: cd backend && uvicorn app.main:app --reload
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Frontend uses the '@' path alias mapped to ./src (configured in tsconfig.json and vite.config.ts)
- One module per approved screen under frontend/src/screens/; App.tsx holds the route table and navigation shell
- Component tests live beside the components they cover, scoped to src/**/*.{test,spec}.{ts,tsx} via Vitest; e2e specs live in frontend/e2e/ and run via Playwright
- Backend follows one router per architecture component (auth, events, public) with Pydantic schemas declaring response models so the OpenAPI document is complete before handlers are implemented
- Backend uses SQLAlchemy 2.0 declarative models with UUID primary keys; tables are auto-created on startup via Base.metadata.create_all (no Alembic migrations yet)
- Session tokens are opaque strings stored in the sessions table (never JWTs); bcrypt-hashed passwords via passlib
- DATABASE_URL defaults to sqlite:///./app.db for zero-config local runs; set DATABASE_URL to switch to PostgreSQL or another engine
- CORS is configured from settings.allowed_origins, falling back to localhost:5173 dev origins
- The Dockerfile runs as an unprivileged user (uid 10001) and includes a /health HTTP healthcheck
- GitHub Actions are pinned to specific commit SHAs; deployment uses OIDC to AWS with no stored secrets
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Backend import errors when running pytest from backend/ | pytest.ini sets pythonpath=. so pytest can import app; ensure you run pytest from the backend/ directory, not the repo root |
| Frontend API calls hit localhost:8000 even when deployed | VITE_API_BASE_URL is baked at build time; set it as an environment variable before running npm run build or npm run dev to point at the correct API |
| Playwright e2e tests fail because backend is not running | playwright.config.ts boots the backend from ../backend/.venv automatically; ensure dependencies are installed there first (cd backend && pip install -r requirements.txt into .venv) |
| CORS errors when the frontend calls the backend in development | The backend allows http://localhost:5173 and http://127.0.0.1:5173 by default; set ALLOWED_ORIGINS to add additional origins if you serve the frontend from a different port |
| PostgreSQL connection failures | The backend defaults to SQLite; if using PostgreSQL, start it with docker compose up -d and set DATABASE_URL to the correct connection string |
